## Структура и границы модулей

```text
app/
  __main__.py        запуск, polling, завершение соединений
  config.py          чтение и проверка настроек
  db.py              создание пула asyncpg
  schema.py          версионный DDL и транзакция миграции
  migrate.py         отдельная команда применения схемы
  repository.py      параметризованный SQL истории и настроек
  context.py         FIFO-усечение полных пар
  assistant.py       координация диалога, история и результат генерации
  operations.py      владелец, общая модель и независимая статистика запросов
  admin.py           формирование статистики для владельца
  admin_setup.py     доверенное назначение владельца в БД
  temperature.py     изолированные тесты температур, хранение и экспорт результатов
  personal_profile.py подтверждённая общая сводка, сжатие и срок хранения
  handlers/personal_profile.py ввод, предпросмотр, подтверждение и удаление сводки
  billing.py         чтение расходов и баланса OpenRouter
  music_profile.py   ограниченный профиль музыканта и срок неиспользования
  retention.py       физическая очистка просроченных данных каждый час
  prompts.py         системные инструкции и few-shot
  llm.py             асинхронный клиент OpenRouter, ошибки и usage
  rendering.py       Telegram HTML и разбиение форматированных ответов
  ui.py              клавиатуры и меню
  text.py            разбиение обычного текста
  telegram.py        единая HTTP-сессия Telegram с прокси
  health.py          служебная проверка готовности
  healthcheck.py     команда проверки состояния
  logging_setup.py   логи со скрытием секретов
  handlers/interface.py кнопки, настройки, ввод профиля и подтверждения
  handlers/temperature.py подготовка и подтверждение теста температур владельцем
  handlers/commands.py  /start, режимы, /settings, /reset
  handlers/admin.py     /admin, периоды, страницы и выбор Qwen/DeepSeek
  handlers/music.py     /profile и явный /search
  handlers/messages.py  личный текст, typing, отправка частей
scripts/            подготовка компьютера и облачный деплой
  experiment.py     ручной эксперимент 12 запусков
tests/              модульные и интеграционные проверки
```

Единственный пул передаётся репозиторию. Обработчики получают `assistant`,
`repository` и `settings` через зависимости Dispatcher. Они не выполняют SQL
и не формируют HTTP-запросы. Значения SQL передаются через `$1`, `$2` и т. д.
Для одного владельца `(chat_id, user_id)` диалог и команды сериализуются
транзакционной advisory-блокировкой PostgreSQL. Разные пользователи независимы.
Если диалог занят, новое сообщение или команда сразу получает просьбу дождаться
завершения и повторить действие. История и настройки не меняются. Попытка,
для которой уже создано событие статистики, отмечается как ошибка `busy` с нулевой
стоимостью; денежные резервы и квоты попыток не применяются.

Командный маршрутизатор подключён **перед общим текстовым**; неизвестные команды
не передаются в LLM. Echo не подключён. Схема проверяется перед polling;
контейнер получает новые env-переменные через Compose. Перед облачным `up`
добавьте LLM-настройки в локальный `.env.cloud`: скрипт деплоя не спрашивает их.

Ответ модели преобразуется из поддерживаемого подмножества Markdown в безопасный
Telegram HTML: заголовки, жирный/курсив, списки, ссылки и код. Сырой HTML
экранируется; ссылки разрешены только HTTP/HTTPS без учётных данных.
Длинный ответ делится на сообщения до 4096 UTF-16 единиц по абзацам, строкам
или пробелам. Если подходящей границы нет, применяется точное разделение по
лимиту. Теги закрываются и восстанавливаются в каждой части; сообщения отправляются
последовательно. При отказе Telegram разобрать HTML используется чистый текст.
[Форматирование Telegram](https://core.telegram.org/bots/api#formatting-options).

LLM-клиент использует уже имеющийся `aiohttp`, поэтому новых зависимостей нет.
Он вызывает `/chat/completions` с таймаутом 30 секунд и лимитом 1500 выходных
токенов по умолчанию, без автоматических
повторов. Непустой ответ с `finish_reason=length` доставляется и сохраняется с
пометкой о незавершённости. Другие незавершённые или пустые ответы отклоняются.
Таймаут, ограничение частоты и некоторые отказы API имеют отдельные безопасные
сообщения. Логи включают HTTP-статус и finish_reason без текста ответа или тела
HTTP-ошибки. Частичный доставленный ответ учитывается как успех; пометка
`result=truncated` присутствует в LLM-логе.
В системную инструкцию передаётся текущий `MAX_OUTPUT_TOKENS` и ориентир объёма:
при 1500 токенах — до 250 русских слов. Сначала модель должна дать законченный
ответ по всем частям вопроса, затем детали без повторов. Перевод не сокращается
до пересказа. Это ориентир для модели, не гарантия точного числа токенов;
исходный пользовательский вопрос не сокращается.
История в БД сохраняется до `/reset`, смены режима или истечения 30 дней, а лимиты ограничивают
именно передаваемый контекст. Незавершённые пары после ошибок в контекст не входят.

Прямые зависимости записаны в `requirements.txt`, инструменты разработки — в `requirements-dev.txt`, проверенные версии транзитивных зависимостей — в `constraints.txt`. При добавлении библиотеки обновите соответствующий requirements-файл, при необходимости ограничения версий, затем повторите start-скрипт. На сервере устанавливаются только зависимости приложения.

При добавлении зависимостей пересоберите целевой Linux-образ. Dockerfile разрешает установку только готовых wheel-пакетов, поэтому успешная сборка подтверждает их доступность для Python 3.12 и Linux x86-64:

```text
docker build --platform linux/amd64 --no-cache -t itmo-tg-template-check .
```

## Тесты

После `start --setup-only` используйте Python из `.venv` (либо активируйте окружение):

```bash
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
python -m pip check
```

Обычный прогон не требует реального токена, прокси или облака. Интеграционный тест с настоящим PostgreSQL включается отдельно и требует работающего Docker:

```powershell
# Windows, после активации .venv
$env:RUN_INTEGRATION = '1'
python -m pytest -m integration -v
Remove-Item Env:RUN_INTEGRATION
```

```bash
# macOS / Linux, после активации .venv
RUN_INTEGRATION=1 python -m pytest -m integration -v
```

Он создаёт собственные контейнер и volume со случайными именами, проверяет пароль, отказ/восстановление БД и сохранность данных, затем удаляет только эти тестовые ресурсы. Учебную БД не использует. После принудительного завершения самого pytest проверьте оставшиеся ресурсы с префиксом `itmo-test-`.

Новые изменения поведения обработчиков и сервисов сопровождайте тестами в стиле Arrange → Act → Assert. Для детерминированных ответов проверяйте точные строки.

# Учебный Telegram-бот: Python + PostgreSQL

## Лабораторная № 1: принятые решения и миграции

Провайдер — OpenRouter, основная модель `deepseek/deepseek-v3.2` с явно
отключённым reasoning. Через `/admin` можно выбрать DeepSeek V3.2 или Qwen.
Для OpenRouter включён приоритет throughput провайдера; скорость не гарантируется,
цена может отличаться от минимальной. Миграция 4 однократно заменяет сохранённые
старые Qwen/DeepSeek на V3.2; последующий ручной выбор Qwen сохраняется.
Без выбора в БД прежний Qwen из env также заменяется основной моделью; другие
явно заданные модели сохраняются.
Режимы: `/study`, `/translate`,
`/music` (создание музыки, аранжировка, саунд-дизайн, сведение и плагины).
В `/music` доступен явный web-поиск командой `/search <вопрос>`; обычные
сообщения поиск не запускают. Стоимость поиска добавляется к стоимости токенов.

Передаваемый контекст ограничен одновременно 40 сообщениями и 8000 символами
истории и музыкального профиля вместе с текущим запросом. Системная инструкция и few-shot-примеры
учитываются отдельно. Старейшие полные пары user/assistant исключаются первыми
(FIFO). Запрос длиннее 8000 символов отклоняется до API. Лимиты задаются через
`HISTORY_MAX_MESSAGES` и `HISTORY_MAX_CHARS`. Это консервативный стартовый бюджет;
40 сообщений допускают больше коротких уточнений, а 8000 символов ограничивают
стоимость повторной передачи подробных ответов.

Настройки LLM: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`,
`LLM_TIMEOUT_SECONDS` (30), `MUSIC_WEB_SEARCH` (`true`/`false`).
Заполните их локально по `.env.example`; ключи никому не передавайте.

Миграция выполняется отдельно от бота, не обращается к Telegram или LLM:

```powershell
.\.venv\Scripts\python.exe -m app.migrate
```

На Linux: `.venv/bin/python -m app.migrate`. PostgreSQL должен быть запущен.
Команда создаёт `schema_migrations`, `user_settings`, `messages`,
`administrators`, `application_settings`, `request_events` и `music_profiles` одной
транзакцией, повторный запуск безопасен. Версия фиксируется в БД; параллельные
запуски сериализуются advisory lock. Существующие данные не удаляются.
Приложение также проверяет схему при запуске, используя свой единственный пул.
Не запускайте бота с действительным токеном во время автоматической проверки.

AI-ассистент студента на основе стартовой обвязки трёх лабораторных курса.
Бот принимает личные текстовые сообщения через **long polling**, сохраняет
историю в PostgreSQL и отвечает через OpenRouter. Echo сохранён только как
неподключённый пример шаблона.

**Локально:** Python работает на вашем компьютере, PostgreSQL — в Docker. **В Yandex Cloud:** оба компонента работают в Docker на одной ВМ. Доступ бота к Telegram из облака проходит через внешний HTTP/SOCKS5-прокси.

## 2. Создать бота и запустить проект

1. Откройте [@BotFather](https://t.me/BotFather) в Telegram, отправьте `/newbot` и следуйте его подсказкам.
2. Сохраните выданный **токен**: это секрет, который даёт управление вашим ботом.
3. Выполните одну команду из корня проекта.

**Windows, PowerShell:**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 --setup-only
```

`Bypass` действует только для этого процесса; политика системы постоянно не меняется. Если запуск ограничен администратором компьютера, следуйте правилам своей организации.

**macOS / Linux, терминал:**

```bash
bash scripts/start.sh --setup-only
```

Скрипт создаст `.venv`, установит зависимости, спросит токен и адрес прокси. **Скрытый ввод не показывает даже звёздочки — это нормально.** Локально вместо прокси можно нажать Enter, если Telegram доступен напрямую. Пароль PostgreSQL генерируется автоматически.

После подготовки БД дополните локальный `.env` переменными LLM из
`.env.example`. Скрипт подготовки сам их не запрашивает. Затем выполните миграцию
командой из начала README и запустите `.\.venv\Scripts\python.exe -m app`
(Linux/macOS: `.venv/bin/python -m app`). Теперь приложение делает реальные
запросы к Telegram и LLM; такие запуски выполняются вручную.
Откройте личный чат и отправьте `/start`, затем учебный вопрос.
Фото, документы, подписи к ним и сообщения групп игнорируются.

Команды: `/study`, `/translate`, `/music` переключают режим и очищают историю;
`/settings` показывает настройки; `/settings 0.7` меняет temperature;
`/reset` удаляет только вашу историю. При переводе укажите язык в тексте запроса.
В `/music` поиск запускается только через `/search <вопрос>`, когда
`MUSIC_WEB_SEARCH=true`. Обычный текст не вызывает поиск. Чтобы запретить
даже явный платный поиск, задайте `false` и перезапустите приложение.
Web-плагин использует Exa с `max_results=3`; этот параметр не означает три
отдельных поисковых запроса. Результаты поиска добавляются провайдером поверх
нашего лимита истории в 8000 символов и тоже могут увеличивать расход токенов.

Первый запуск требует интернета для скачивания Python-зависимостей и образа PostgreSQL. Повторные запуски сохраняют настройки и БД; зависимости переустанавливаются при изменении файлов их версий.

## 3. Что такое .venv и как разрабатывать в IDE

`.venv` — отдельная папка с интерпретатором Python и библиотеками **этого проекта**. Она предотвращает конфликты с зависимостями других проектов. Её не нужно редактировать, копировать на сервер или добавлять в Git. Скрипт создаёт её сам.

Для работы в IDE подготовьте окружение и БД, не запуская второй процесс бота:

```powershell
# Windows
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 --setup-only
```

```bash
# macOS / Linux
bash scripts/start.sh --setup-only
```

В **VS Code** установите расширение Python от Microsoft, выполните `Python: Select Interpreter` и выберите `.venv`. В **PyCharm**: Settings → Project → Python Interpreter → Existing environment.

Путь интерпретатора:

- Windows: `.venv\Scripts\python.exe` внутри проекта.
- macOS/Linux: `.venv/bin/python` внутри проекта.

В конфигурации запуска IDE укажите **модуль `app`**, рабочую папку — корень проекта, интерпретатор — из `.venv`. Не запускайте `app/__main__.py` как отдельный файл. Переменные загрузятся из `.env` автоматически. Здесь можно ставить breakpoints и запускать отладчик.

То же самое из терминала:

```powershell
.\.venv\Scripts\python.exe -m app
```

```bash
.venv/bin/python -m app
```

Активация окружения необязательна: явный путь к Python уже выбирает `.venv`. Если предпочитаете активацию, используйте `.\.venv\Scripts\Activate.ps1` или `source .venv/bin/activate`, после чего команда запуска — `python -m app`.

После изменения кода остановите бот через **Ctrl+C** или Stop в IDE и запустите снова. Автоматическая перезагрузка не включена. Остановка бота не удаляет и не останавливает PostgreSQL.

## 4. Настройки: .env и .env.cloud

`.env` — обычный текстовый файл формата `ИМЯ=значение`. Он уже создаётся скриптом. Для ручной настройки скопируйте `.env.example` в `.env`. Сохраняйте файл в UTF-8. `.env.cloud` создаётся отдельно при первом деплое; токен и прокси для облака вводятся отдельно, пароль облачной БД тоже отдельный.

| Переменная           | Назначение                                             | Значение по умолчанию                                    |
| -------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| `BOT_TOKEN`          | Токен от BotFather                                     | Обязательно                                              |
| `TELEGRAM_PROXY_URL` | HTTP CONNECT / SOCKS5-прокси для всех вызовов Telegram | Пусто локально; обязательно в облаке                     |
| `POSTGRES_HOST`      | Адрес БД                                               | `127.0.0.1` локально, `db` внутри облачного Compose      |
| `POSTGRES_PORT`      | Порт БД                                                | `5432`; локально можно изменить при конфликте портов     |
| `POSTGRES_DB`        | Имя базы                                               | `bot`                                                    |
| `POSTGRES_USER`      | Пользователь БД                                        | `bot`                                                    |
| `POSTGRES_PASSWORD`  | Пароль БД                                              | Скрипт генерирует при первоначальной настройке           |
| `LOG_LEVEL`          | Подробность логов                                      | `INFO`; доступны `DEBUG`, `WARNING`, `ERROR`, `CRITICAL` |
| `HEALTH_PORT`        | Локальный служебный HTTP-порт                          | `8080`                                                   |

Примеры прокси с вымышленными адресами:

```dotenv
TELEGRAM_PROXY_URL='http://student:password@proxy.example:3128'
# Или:
TELEGRAM_PROXY_URL='socks5://proxy.example:1080'
```

Если логин/пароль прокси содержит `@`, `:`, `/`, кодируйте их в URL как `%40`, `%3A`, `%2F`. Для паролей со знаком `$` или `#` используйте одинарные кавычки в env-файле. Подстановки `${OTHER_VARIABLE}` внутри значений не используются. Не записывайте реальные секреты в примеры, скриншоты и задания для публичных ИИ-сервисов.

Прокси должен быть доступен **с ВМ**, поддерживать HTTP CONNECT либо SOCKS5 и выход в Telegram. Прокси предоставляет преподаватель или студент; шаблон его не создаёт. Telegram MTProto-прокси из настроек мобильного приложения сюда не подходит. При отказе указанного прокси прямого обхода нет. Настройка относится к Telegram; будущие LLM/MCP-клиенты студенты настраивают отдельно.

Переменные окружения процесса имеют приоритет над env-файлом. При облачном деплое передаются их эффективные значения, но адрес БД внутри Compose всегда `db:5432`. В обычной работе достаточно редактировать соответствующий env-файл. Чтобы напрямую запустить приложение с другим файлом: `python -m app --env-file .env.cloud` (адрес `db` разрешается только внутри Docker-сети).

**Не меняйте пароль созданной БД только в env-файле:** PostgreSQL применяет начальные имя/пользователя/пароль при создании пустого volume. Для смены пароля существующей роли нужна команда SQL `ALTER ROLE` и согласованное обновление настроек. Если данные нужны, не удаляйте volume ради исправления пароля.

`.env`, `.env.cloud`, `.venv` и `.deploy` исключены из Git. Секреты не попадают в Docker build context. На Linux/macOS файлы с секретами получают права `600`; на Windows доступ определяется также ACL вашей пользовательской папки. Не размещайте проект в общедоступной папке.

## 5. Управление локальным окружением и healthcheck

В таблице `start` означает `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1` на Windows или `bash scripts/start.sh` на macOS/Linux.

| Команда              | Что делает                                                                    |
| -------------------- | ----------------------------------------------------------------------------- |
| `start`              | Подготавливает окружение и запускает бот в терминале                          |
| `start --setup-only` | Подготавливает БД и `.venv` для работы в IDE                                  |
| `start health`       | Проверяет уже работающий бот и реальный запрос к БД                           |
| `start status`       | Показывает состояние контейнера PostgreSQL                                    |
| `start logs`         | Показывает последние 100 строк логов PostgreSQL                               |
| `start stop`         | Останавливает PostgreSQL, сохраняя данные; бот предварительно остановите сами |

Логи локального бота видны в терминале/IDE, где он запущен.

Проверка приложения также доступна через `python -m app.healthcheck` из `.venv` и по адресу [http://127.0.0.1:8080/health](http://127.0.0.1:8080/health).

```json
{ "status": "ok", "database": "ok", "polling": "running" }
```

`200` означает: начальная проверка Telegram пройдена, задача polling работает, активный пул приложения выполнил `SELECT 1`. При отказе БД или неготовности — `503`; команда healthcheck возвращает ненулевой код. Остановите PostgreSQL и повторите проверку, затем запустите `start --setup-only`: после восстановления БД статус вернётся к `200`.

`pg_isready` внутри контейнера проверяет готовность PostgreSQL принимать соединения; `SELECT 1` проверяет подключение **самого приложения с его паролем**. Это разные проверки. Healthcheck не делает постоянные запросы в Telegram и не гарантирует его текущую сетевую доступность: сетевые ошибки polling смотрите в логах.

Для SQL-клиента (DBeaver, DataGrip и т. п.) используйте значения из локального `.env`. Порт БД опубликован только на `127.0.0.1`. В облаке PostgreSQL не опубликован вообще.

Данные сохраняются в именованном Docker volume. Имя локального Compose-проекта вычисляется из полного пути: русские имена каталогов поддерживаются, но перенос папки в другое место создаёт другое имя проекта/volume. При переносе сначала сделайте резервную копию данных и перенесите их отдельно. Старый volume автоматически не удаляется.

## 6. Где писать лабораторные

```text
app/
  __main__.py        запуск, polling, завершение соединений
  config.py          чтение и проверка настроек
  db.py              создание пула asyncpg
  schema.py          версионный DDL и транзакция миграции
  migrate.py         отдельная команда применения схемы
  repository.py      параметризованный SQL истории и настроек
  context.py         FIFO-усечение полных пар
  assistant.py       координация диалога, история и результат генерации
  operations.py      владелец, общая модель и независимая статистика запросов
  admin.py           формирование статистики и бюджета для владельца
  admin_setup.py     доверенное назначение владельца в БД
  billing.py         чтение бюджета OpenRouter без вызова модели
  music_profile.py   ограниченный профиль музыканта и срок неиспользования
  retention.py       физическая очистка просроченных данных каждый час
  prompts.py         системные инструкции и few-shot
  llm.py             асинхронный клиент OpenRouter, ошибки и usage
  text.py            разбиение длинных ответов
  telegram.py        единая HTTP-сессия Telegram с прокси
  health.py          служебная проверка готовности
  healthcheck.py     команда проверки состояния
  logging_setup.py   логи со скрытием секретов
  handlers/commands.py  /start, режимы, /settings, /reset
  handlers/admin.py     /admin, периоды, страницы и выбор Qwen/DeepSeek
  handlers/music.py     /profile и явный /search
  handlers/messages.py  личный текст, typing, отправка частей
scripts/            подготовка компьютера и облачный деплой
  experiment.py     ручной эксперимент 12 запусков
tests/              тесты обвязки и восьми сценариев лабораторной
```

Единственный пул передаётся репозиторию. Обработчики получают `assistant`,
`repository` и `settings` через зависимости Dispatcher. Они не выполняют SQL
и не формируют HTTP-запросы. Значения SQL передаются через `$1`, `$2` и т. д.
Для одного владельца `(chat_id, user_id)` диалог и команды сериализуются
транзакционной advisory-блокировкой PostgreSQL. Разные пользователи независимы.
Если диалог занят, новое сообщение или команда сразу получает просьбу дождаться
завершения и повторить действие. История и настройки не меняются. Попытка,
для которой уже создано событие статистики, отмечается как ошибка `busy` с нулевой
стоимостью и освобождённым резервом; она учитывается в квоте попыток.

Командный маршрутизатор подключён **перед общим текстовым**; неизвестные команды
не передаются в LLM. Echo не подключён. Схема проверяется перед polling;
контейнер получает новые env-переменные через Compose. Перед облачным `up`
добавьте LLM-настройки в локальный `.env.cloud`: скрипт деплоя не спрашивает их.
Деплой в рамках автоматической разработки не выполнялся.

LLM-клиент использует уже имеющийся `aiohttp`, поэтому новых зависимостей нет.
Он вызывает `/chat/completions` с таймаутом 30 секунд и лимитом 1500 выходных
токенов по умолчанию, без автоматических
повторов. Незавершённый ответ (`finish_reason` не `stop`) считается ошибкой.
Логи содержат только метаданные вызова; текст HTTP-ошибки провайдера не пишется.
История в БД сохраняется до `/reset`, смены режима или истечения 30 дней, а лимиты ограничивают
именно передаваемый контекст. Незавершённые пары после ошибок в контекст не входят.

Прямые зависимости записаны в `requirements.txt`, инструменты разработки — в `requirements-dev.txt`, проверенные версии транзитивных зависимостей — в `constraints.txt`. При добавлении библиотеки обновите соответствующий requirements-файл, при необходимости ограничения версий, затем повторите start-скрипт. На сервере устанавливаются только зависимости приложения.

При добавлении зависимостей пересоберите целевой Linux-образ. Dockerfile разрешает установку только готовых wheel-пакетов, поэтому успешная сборка подтверждает их доступность для Python 3.12 и Linux x86-64:

```text
docker build --platform linux/amd64 --no-cache -t itmo-tg-template-check .
```

## 7. Первый деплой в Yandex Cloud

Подготовьте личный аккаунт Yandex Cloud, активный платёжный аккаунт и каталог. Нужны права на создание и удаление Compute/VPC-ресурсов в этом каталоге (например, роль `editor` на выделенном учебном каталоге) и доступные квоты на одну ВМ, диск и публичный IP. [Начало работы с yc](https://yandex.cloud/ru/docs/cli/quickstart).

Нужен внешний HTTP/SOCKS5-прокси, доступный из облака. Желательно создать **второго бота для облака**: с одним токеном нельзя одновременно запускать два процесса polling. Если токен общий, перед деплоем остановите локального бота; перед локальным запуском остановите облачную ВМ.

Подключитесь к сети или VPN, через которые будете работать с сервером, и определите публичный IPv4 компьютера.

**Windows (PowerShell):**

```powershell
(Invoke-RestMethod 'https://api.ipify.org?format=json').ip
```

**macOS (Терминал):**

```bash
curl -4 https://api.ipify.org
```

**Linux (терминал):**

```bash
curl -4 https://api.ipify.org
```

К полученному адресу добавьте `/32`. Например, если команда вывела `203.0.113.10`, передайте скрипту `203.0.113.10/32`. Этот адрес разрешается для подключения по SSH. Повторите проверку, если сменили сеть или настройки VPN. Приведённый адрес — только пример, замените его своим.

Запустите деплой:

**Windows:**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\deploy.ps1 up --ssh-cidr 203.0.113.10/32
```

**macOS / Linux:**

```bash
bash scripts/deploy.sh up --ssh-cidr 203.0.113.10/32
```

Сценарий спросит облачный токен и прокси, подготовит `.env.cloud`, установит отсутствующий `yc` **официальным установщиком** и при необходимости запустит `yc init`. Вход в браузере и выбор облака/каталога выполняете вы. Учётные данные yc остаются на вашем компьютере; на ВМ они не передаются.

Если в выбранном каталоге есть сеть с именем `default`, сценарий использует её и не тратит квоту на ещё одну сеть. Если такой сети нет, он создаёт отдельную сеть проекта. Затем создаются отдельные подсеть, группа безопасности и **обычная, непрерываемая ВМ**:

| Параметр              | Значение                            |
| --------------------- | ----------------------------------- |
| Платформа / зона      | `standard-v2` / `ru-central1-a`     |
| Процессор             | 2 vCPU, гарантия 5%                 |
| Память                | 1 ГБ RAM + 1 ГБ swap                |
| Диск / ОС             | 20 ГБ HDD, Ubuntu 24.04 LTS         |
| Входящие подключения  | Только TCP 22 с вашего `--ssh-cidr` |
| Исходящие подключения | Интернет, включая внешний прокси    |

Это экономная стартовая конфигурация для обвязки. LLM предполагается внешний, локальные модели на этой ВМ не запускаются. Достаточность для итоговой студенческой реализации нужно проверять отдельно. Конфигурацию можно выбрать **при первом создании**, например `--memory 2` или `--platform standard-v3 --core-fraction 20`; более мощные варианты дороже. Параметры сохраняются для повторных запусков. Изменение существующей ВМ этим скриптом не выполняется.

`cloud-init` устанавливает Docker и swap. Скрипт по SSH передаёт код и конфигурацию, собирает образ и ждёт успешного healthcheck. Вывод cloud-init и Docker Compose показывается в терминале по мере выполнения; передача секретов остаётся скрытой. Первый деплой может занять несколько минут. Ключ проекта и состояние ресурсов сохраняются в `.deploy`; не удаляйте эту папку, пока ресурсы существуют. Первый SSH-контакт сохраняет ключ сервера в отдельный known_hosts; последующая неожиданная смена ключа останавливает подключение.

Токен/пароли передаются по зашифрованному stdin SSH. Они не помещаются в cloud-init, аргументы процессов или Docker-образ. Запуск Docker после перезагрузки восстанавливает контейнеры. Состояние `unhealthy` видно в Docker, но само по себе не перезапускает контейнер; политика `unless-stopped` перезапускает завершившийся процесс.

## 8. Обновление, остановка и удаление облака

Здесь `deploy` означает соответствующий `deploy.ps1` или `deploy.sh` из предыдущего раздела.

| Команда                                | Что делает                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| `deploy up`                            | Обновляет код и конфигурацию, пересобирает бот; БД сохраняется                       |
| `deploy status`                        | Показывает состояние ВМ и контейнеров                                                |
| `deploy logs`                          | Показывает последние 100 строк логов бота и PostgreSQL                               |
| `deploy stop`                          | Останавливает всю ВМ; диск с БД сохраняется и продолжает тарифицироваться            |
| `deploy start`                         | Запускает ВМ и ждёт готовности контейнеров                                           |
| `deploy access --ssh-cidr НОВЫЙ_IP/32` | Меняет разрешённый адрес SSH после смены сети                                        |
| `deploy destroy`                       | Удаляет созданные ресурсы проекта вместе с диском и данными БД; общая сеть `default` остаётся |

Повторный `up` берёт код из вашей текущей папки, включая незакоммиченные изменения Python-файлов в `app`. Он не делает commit/push и не требует публичного репозитория. Если добавите ресурсы приложения другого типа (например, шаблоны или SQL-файлы), дополните явный список упаковки в `source_archive` и `COPY` в Dockerfile.

Идентификаторы, каталог и метка `template-id` проверяются перед действиями. При частичном сбое ничего автоматически не удаляется: `.deploy/state.json` позволяет повторить команду. После ошибки ресурсы могут продолжать тарифицироваться. Обычное удаление затрагивает только созданные этим проектом ресурсы; чужой каталог или чужие метки приводят к отказу.

Если деплой прервался после остановки старого бота, устраните причину и повторите `deploy up`: автоматического отката версии нет, volume БД остаётся. Не запускайте два деплоя одного проекта одновременно. Не удаляйте `.deploy/state.json` для обхода ошибки — так можно потерять связь с платными ресурсами.

У ВМ динамический публичный IP: после остановки/запуска он может измениться, скрипт заново получает адрес через yc. Перед `destroy` самостоятельно экспортируйте нужные данные, например `pg_dump` по SSH. Резервные копии этим учебным шаблоном автоматически не создаются. После удаления проверяйте раздел биллинга своего облака, особенно если создавали дополнительные ресурсы вручную.

## 13. Админ-панель владельца

`/admin` доступна только в личном чате пользователю, записанному в таблице
`administrators`. Telegram ID не хранится в исходниках или env. Владелец ровно
один; пока он не назначен, доступ закрыт для всех. Назначение требует
доверенного доступа к серверному терминалу и не выполняется через Telegram.

После обновления контейнеров и настройки PostgreSQL выполните на сервере:

```bash
docker compose --profile cloud run --rm bot python -m app.admin_setup
```

Введите свой числовой user ID в скрытом вводе. Команда не печатает ID,
не обращается к Telegram или LLM, применяет миграцию и сохраняет владельца
в PostgreSQL. При первой настройке выбирается Qwen. Повторный запуск с тем же
ID не меняет выбранную модель; с другим ID — отклоняется. Локально:
`.venv/Scripts/python.exe -m app.admin_setup` (Windows) или
`.venv/bin/python -m app.admin_setup` (Linux/macOS).

Панель показывает запросы за 24 часа / 7 дней / всё время, пользователей,
успехи, ошибки, незавершённые попытки, учтённые токены и стоимость.
Список всех пользователей разбит на страницы по 10; показаны ID и агрегаты,
без текстов диалога. Авторизация проверяется при каждом открытии и callback,
а смена модели дополнительно проверяет владельца в SQL.

Кнопки выбора Qwen и DeepSeek сохраняют общую модель в `application_settings`.
Новые запросы всех пользователей используют её без перезапуска; начавшиеся
заканчиваются на прежней модели. История сохраняется. `/settings` показывает
действующую модель. `LLM_MODEL` — начальное значение, пока выбор не сохранён
в БД; изменение env не перекрывает выбор администратора.

Статистика в `request_events` независима от истории: `/reset` и смена режима
её не удаляют. Учитываются попытки LLM после установки админки, не команды
и не отклонённый ввод. Событие создаётся до LLM и завершается после обработки;
аварийно прерванные попытки могут оставаться «не завершено». Стоимость берётся
из `usage.cost`, включая неполные ответы, если провайдер её вернул. При таймауте
стоимость может быть неизвестна — это не ноль. Покрытие стоимости показано
отдельно. Экспериментальный скрипт в статистику бота не включается.

`GET /api/v1/key` OpenRouter используется с обычным `LLM_API_KEY` для расхода
и остатка лимита ключа. Это не общий баланс аккаунта. Для общего баланса
необязательно задайте `OPENROUTER_MANAGEMENT_KEY`: отдельный management key
позволяет читать `GET /api/v1/credits`. Баланс — `total_credits - total_usage`.
Без management key или при сбое API показано «недоступно». Общие расходы
могут включать другие приложения и эксперименты. Не передавайте ключи в Telegram.

### Существующий автодеплой VDS

`.github/workflows/deploy.yml` запускается при push в `main` или вручную
через `workflow_dispatch`. Он делает `git pull origin main` на сервере
и `docker compose --profile cloud up -d --build --wait --wait-timeout 180`.
Workflow ждёт готовности сервисов; при ошибке выводит статус и последние логи
и завершается с ненулевым кодом. Автоматического отката нет. Нужен Docker Compose
с поддержкой `--wait` и `--wait-timeout`. Этот workflow использует
серверный `.env` по умолчанию: `--env-file` не указан. Это отличается
от скриптов `scripts/deploy.*`, работающих с `.env.cloud`.

До push в `main` подготовьте LLM-настройки в серверном `.env` по безопасному

## 14. Расходы, музыкальный профиль и сроки хранения

По умолчанию действуют:

| Настройка | Значение | Назначение |
|---|---|---|
| `DAILY_BUDGET_USD` | 2 | Внутренний суточный бюджет всего бота |
| `USER_DAILY_BUDGET_USD` | 0.20 | Суточный бюджет одного пользователя |
| `REQUEST_RESERVE_USD` | 0.05 | Резерв перед допуском одной попытки |
| `MAX_OUTPUT_TOKENS` | 1500 | Предел генерации ответа |
| `USER_REQUESTS_PER_MINUTE` | 3 | Пользовательские попытки за скользящую минуту |
| `USER_REQUESTS_PER_DAY` | 50 | Пользовательские попытки за сутки UTC |
| `HISTORY_RETENTION_DAYS` | 30 | Возраст сообщений диалога |
| `STATISTICS_RETENTION_DAYS` | 90 | Возраст статистики запросов |
| `MUSIC_PROFILE_RETENTION_DAYS` | 180 | Неиспользование музыкального профиля |

Перед вызовом API бюджет проверяется и резервируется одной короткой
транзакцией PostgreSQL. Если свободной суммы недостаточно или превышена
частота/квота, LLM не вызывается. Известная `usage.cost` заменяет резерв;
при неизвестной стоимости резерв остаётся занятым в суточном счётчике.
Сутки считаются в UTC, счётчик допуска начинается заново в 00:00 UTC.
`/admin` показывает внутренний бюджет с резервами отдельно от данных OpenRouter.
Команды профиля, режима, настроек и админки не расходуют квоту LLM.

Резерв — консервативная оценка, не тарифная гарантия провайдера. Фактическая
стоимость может отличаться, а часть списаний при таймауте остаётся неизвестной.
Поэтому на выделенном ключе OpenRouter также установите лимит расходов.
Вызовы других приложений и вручную запущенный эксперимент внутренними
квотами бота не ограничиваются. Агент настройки реального ключа не менял.

Пример музыкального профиля:

```text
/profile daw Ableton Live
/profile os Windows
/profile genres drum and bass, ambient
/profile plugins штатные устройства Ableton
/profile equipment наушники и MIDI-клавиатура
/profile budget до $100 на плагины
/profile level начинающий
/profile
```

Каждое поле — до 240 символов. Бюджет профиля относится к музыкальным покупкам,
а не к API. `/profile clear` удаляет профиль; `/reset` его сохраняет. Профиль
используется только в `/music` и только для своего пользователя. Он включается
в бюджет 8000 символов; если текущий запрос занимает весь бюджет, профиль
пропускается для этого запроса, сам запрос не обрезается.

Для актуальной информации о плагине отправьте `/search <вопрос>` в режиме
`/music`. Это явный платный поиск. Указание «найди» в обычном сообщении само
по себе поиск не включает. Поиск использует ту же модель и те же ограничения,
что обычный диалог. Качество советов и источников студент проверяет вручную.

История старше 30 дней и профиль после 180 дней без использования не
возвращаются в контекст даже до очистки. Панель не показывает статистику
старше 90 дней. Просмотр, изменение профиля и обращения в `/music` обновляют
его последнее использование. Физическая очистка стартует вместе с приложением
и повторяется каждый час; удаление может задержаться до часа после порога.
Настройки режима/temperature и запись владельца этой очисткой не удаляются.
Политика относится к активной БД; резервными копиями проект не управляет.

Переработка под высокую нагрузку отложена по решению владельца. Настоящие
PostgreSQL/Docker, серверное назначение владельца, живой баланс и качество
`/music` остаются для ручной проверки. Push и автодеплой агентом не выполнялись.
